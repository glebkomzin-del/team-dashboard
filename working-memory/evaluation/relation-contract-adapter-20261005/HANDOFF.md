## Admission rule and integration limit

`relation_adapter.py` accepts only a complete typed response: case/action IDs, relation enum, and arrays of existing original IDs for earlier/later/object/action/prerequisite/replacement/competing evidence. The transport schema has no free quote, final statement, owner, condition, summary, or task field. Duplicate/missing actions, invalid IDs, unknown fields, reversed chronology, missing positive evidence, changed source map, or absent independent verified binding yield `REVIEW_REQUIRED`, with no automatic work. A positive `replaced`/`expressly_withdrawn` decision is **only** `exclude_new_candidate_only` for the returned case/action; no historical cancellation is authorized. `unclear` stays in review even with a trusted binding. Original HumanReview upload-work count 0 and Caroline-related count 2 are not inputs to, or mutated by, the adapter.

The offline positive fixture has a fixed expected-ID oracle; it does **not** constitute an independently verified production binding. Before runtime integration, the caller must bind an immutable meeting candidate/source revision and independently verified original-ID relation to that exact candidate, then apply only its result while preserving existing human-review references. The source-grounded final observations must be the single input for any future-summary rebuild; appending a new summary to the old, potentially contradictory summary is outside this adapter and remains an open integration requirement. The current V4+archive-overlay runtime has not been patched or tested with this adapter. No live semantic admission, deployment, or product-wide semantic acceptance is claimed.

On failure, keep all automatic candidate changes disabled; on pass, advance only to a separately reviewed runtime integration proposal.
